# Agent Note: Stable release update ownership

Status: implemented

English | [中文](2026-08-24-stable-release-update-ownership.zh.md)

## Problem

A signed manifest policy, durable update preference, filesystem transaction, and release workflow have different authority. Combining them could let untrusted release data become durable, let Runtime mutate an installation, or let verification jobs perform signing or publication. Release evidence also needs a precise completion point so a partially written manifest set cannot be consumed.

## Decision

`@harness-desktop/dsh-update-policy` owns signed-manifest parsing and selection, public release-policy parsing, and restricted HTTPS reads. It verifies the exact record, canonical Ed25519 signature, application, channel, consumer, platform, architecture, format, version, HTTPS origin, digest syntax, and safe archive members. Its in-memory `VerifiedUpdateArtifact` retains the authenticated URL only for the immediate downloader; Runtime records, native journals, and worker requests contain no release URL, key, signature, or raw manifest.

Runtime owns the selected Desktop channel and the last durable redacted outcome in its existing settings provider. The stored channels are `stable`, `beta`, and `nightly`; stored outcome kinds are `up-to-date`, `staged`, `applied`, `rolled-back`, and `failed`. Its fixed codes are `unconfigured-update-source`, `up-to-date`, `staged`, `applied`, `rolled-back`, `manifest-rejected`, `artifact-rejected`, `health-check-failed`, and `install-failed`. The durable record contains only version, channel, kind, code, and an optional last-known-good version. A recovery process does not schedule a second automatic check after rollback; later Main processes suppress only the exact version and channel recorded as a health-check rollback from their current installed version. An unreadable outcome fails closed, while a different candidate remains eligible.

Packaged Desktop Main loads `update-policy.json` from its resources and begins one automatic check only after the authenticated Dashboard publishes. Main admits that check, download, staging, native handoff, and outcome persistence as one lifecycle flight; shutdown closes admission, aborts remote reads, and waits for local staging or rollback settlement before Runtime teardown. Windows NSIS, macOS with a universal ZIP candidate, and Linux AppImage own native replacement; Debian packages leave replacement to the system package manager. `NativeDesktopInstallAdapter` downloads the candidate and a retained rollback artifact for the exact installed version through policy endpoints, synchronizes each private file and parent directory entry, and records a transaction journal. The packaged detached worker and every emitted Main chunk it imports are copied as exact resources, so the worker can continue after the installed application starts replacing itself. On Windows, its constrained environment retains non-secret user state and TLS paths, including `HARNESS_HOME`, `TEMP`, and `NODE_EXTRA_CA_CERTS`, while excluding ambient credentials. It derives required machine paths from `SystemRoot`, and candidate, rollback, and restored Desktop launches use the validated application directory as their working directory so OS caches cannot resolve below private worker storage. A private journal replacement keeps its synchronized sibling, retries only transient Windows sharing errors within `nativeWorkerReadyTimeoutMs`, and leaves the prior journal in place when that bound expires. An external worker outside the installation root rechecks both digests and snapshots both installers before Main may exit. The public policy separately bounds that preparation with `nativeWorkerReadyTimeoutMs`; `healthCheckTimeoutMs` bounds waiting for the old process and, after installation, candidate Dashboard health. An old-process timeout leaves the stable installation unchanged. macOS publishes a candidate `.app` through Foundation's atomic fixed-path replacement instead of two directory renames, so process interruption cannot leave the configured `.app` name absent. After it installs the candidate, the Windows worker passes one 128-bit launch nonce only through the candidate argv and publishes the same nonce in the transaction heartbeat; Main accepts only that exact pair and a non-future timestamp. Other platforms retain the process-start time check. The worker tracks the candidate's exact process-tree identity; a restarted candidate without valid heartbeat proof schedules rollback before Dashboard health. The worker accepts only the matching Dashboard health acknowledgement; a failed candidate launch, candidate process-tree exit, candidate health deadline, malformed journal, or rollback request terminates the candidate tree and installs the retained release. Automatic rollback publishes a transaction-bound completion marker after the retained installer succeeds and before launching the stable application, so only that stable version can report rolled-back health. Runtime records a terminal outcome before Main atomically changes the journal to `cleanup-pending`; process restart then resumes idempotent cleanup of known transaction markers, caches, and journal while preserving unknown entries. Successful staging, application, and restored health failure map to Runtime `staged`/`staged`, `applied`/`applied`, and `rolled-back`/`health-check-failed`; other failures map to redacted `failed` outcomes.

Serialized plans and detached-worker marker paths use `plan.platform`; Main reads its private cache with the executing Node platform. These path domains do not substitute for one another.

On Windows, Main copies the packaged `windows-native-update-supervisor.exe` into the private worker directory and never executes the installed resource in place. The dependency-free AMD64 GUI supervisor owns the PowerShell worker and installer descendants through a Job Object while Main retains startup ownership until the UUID-bound readiness record is stable. A readiness failure uses a private cancellation request; Main removes private inputs only after the supervisor drains the Job, publishes the matching acknowledgement, and exits with the cancellation-complete code. Candidate and rollback NSIS installers receive the validated application directory through a final `/D=` argument instead of relying on registry installation state. Terminal journal identity uses the exact Candidate Job PID and executable path without comparing separately estimated cross-process epoch starts. Candidate and restored Desktop processes use the explicit breakaway path and therefore outlive successful supervisor settlement without letting installer descendants escape.

Each NSIS package copies a one-use policy-state marker. Its post-copy installer macro retains `resources/update-policy.json` only after it reads the exact new `present` marker; an absent, unreadable, or malformed marker deletes the policy, then the macro removes the marker itself. If either removal fails, the installer aborts rather than starting with inherited trust. A successor that intentionally omits policy therefore cannot inherit predecessor trust, while a successor with policy retains only its own policy regardless of predecessor uninstaller behavior.

The CLI owns its package-manager guidance and standalone payload transaction without using Runtime state. An npm layout prints `npm update -g @harness-desktop/cli` without executing it. A standalone archive keeps its launcher and recovery entry outside `payload/current`; the updater loads the public policy from that fixed root, verifies a newer candidate manifest and a rollback manifest for its current version, then downloads and checks candidate bytes, members, and executable paths. A compact signed member list containing only `manifest.json` is accepted only when that archive-local catalog enumerates every safe member; executable paths are then checked against those verified catalog members. A launcher-visible phase journal and deterministic `payload/retained` path let the next invocation conservatively restore the last stable payload after interruption at any rename. An exclusively created lock rejects a second staging transaction; its unpredictable ownership token remains held through replacement, process-tree health settlement, rollback, and private-file cleanup. A matching live owner remains authoritative after its diagnostic expiry, including a POSIX owner whose image moved from `payload/current` to `payload/retained`; only a dead or mismatched owner permits recovery. Windows uses ZIP; macOS and Linux use tar.gz to preserve executable modes. The native Linux artifact row rebuilds `node-pty` in the matching manylinux 2.28 image before Desktop and standalone CLI assembly, rejecting a missing binding or newer GLIBC requirement. After the deploy install intentionally skips package scripts, the CLI packer copies that exact binding into its deployed `node-pty` package and retains it in the package files allowlist. Both Linux AppImage and Deb inspection require the resulting binding, while standalone assembly and archive verification require that target binding and, when Koffi is packaged, both `linux_<arch>` and `musl_<arch>` Koffi binaries. A missing or foreign native module rejects the archive before it can serve as release evidence. macOS and Linux release the verified lock after switching and health-checking in the command process; Windows hands the exact lock, journal, and fixed payload paths to a system PowerShell worker, which assumes lock ownership before readiness and rechecks it before replacement and final removal. That worker waits for the command process to exit, switches the payload, checks the bundled Node and CLI entrypoint as one process tree, and restores the retained payload on health failure. Missing or invalid policy returns `unconfigured-update-source` before candidate I/O or mutation.

A manual rollback has one installer owner. On Windows, a transaction-named local mutex permits only the worker that writes the matching completion marker to run NSIS and relaunch the stable application. On macOS and Linux, Main publishes `rollback-scheduled` only after the fresh rollback worker is ready; the existing watchdog then yields without restoring bytes.

## Release evidence and approvals

`writeUpdateManifests()` prepares every target manifest in memory, reserves the final output root with one exclusive directory creation, writes the set into a private inner stage, and renames that stage to `ready`. It reads an Ed25519 private key only after artifact inventory completes, signs each exact target, and rechecks the result through the shared policy. A competing root owner remains untouched, and failure cleanup never recursively removes the reserved root.

The credential-free Desktop artifact workflow packages with `--publish never`, an ephemeral public policy, and signing disabled. Every row reads each produced artifact once through a stable no-follow handle, writes exact private snapshots, and uses only those snapshots for inventory, ephemeral Ed25519 signing, manifest verification, digest binding, evidence collection, and product upload. `DSH_UPDATE_SNAPSHOT_ROOT` selects the root shared by verification, evidence collection, and upload: CI pins it to `dist/ci-update-snapshots` in a clean checkout, and a complete local evidence run must select its own fresh child explicitly. A verifier-only local invocation without that variable reserves a fresh `dist/update-snapshots-*` child and never deletes or replaces an earlier root; the collector refuses to infer a root or fall back to stale CI snapshots. The evidence collector rehashes both artifact and manifest snapshots and rejects any binding mismatch. Native CI owns test-identity healthy-commit and watchdog-rollback evidence on each self-updating target: Windows NSIS, macOS universal ZIP, and Linux AppImage with a real FUSE runtime; the macOS ephemeral policy contains candidate and rollback endpoints for both Intel and Apple Silicon CLI tar.gz archives under one build/verify outcome. Each row also owns the matching Windows CLI ZIP, Linux CLI tar.gz archive, macOS `lipo` inspection, and Linux Deb inspection. Each row always uploads a redacted artifact-hash and check-outcome record, while product snapshots upload only after the row succeeds. The AppImage policy proves its self-update target; the Deb policy is parsed as an embedded resource but needs no self-update endpoint. One host's local or cached artifacts do not prove another native row or a fresh independent archive.

The Desktop `prepackage` and `prepackage:dir` lifecycle hooks run the cross-platform native preparation command before Electron Builder; it rebuilds and validates the native supervisor from the current C source on Windows x64 and skips other platforms. The artifact workflow relies on those package entry points instead of compiling the supervisor separately. A Windows-only directory FileSet selects exactly `windows-native-update-supervisor.exe` from the x64 native output and copies it to `resources/windows-native-update-supervisor.exe`; macOS and Linux configurations do not declare or carry it, and `.obj` or unrelated output is excluded. Directory copying reaches Electron Builder's extra-file transformer for that EXE. Credential-free CI sets `signExecutable` to false, so Electron Builder returns no signing transformer before identity discovery; a separately approved release build instead supplies its ordinary `signIf()` after-copy operation without supervisor-specific credentials or signing code. Unsigned verification requires the final NSIS resource and `win-unpacked` resource to match the current native-build bytes and identifies both as AMD64 Windows GUI PE images. A signed release requires separate Authenticode and approved-signer evidence because signing intentionally changes the copied resource bytes.

Production update trust remains a separate operator prerequisite: the public key, configured exact HTTPS origin, and release location require independent audit before either updater can run. A build with `DSH_DESKTOP_SIGNING_MODE=release` must also provide a valid public-only `DSH_DESKTOP_UPDATE_POLICY` and forces Electron Builder code signing, so absent or unusable signing material fails rather than emitting an unsigned release; the standalone CLI builder requires its matching `DSH_UPDATE_POLICY`. Windows signing, macOS notarization, production update-manifest signing, npm publication, update upload, and GitHub Release creation are separate approval actions. The manual candidate workflow only validates that exactly one future operation was selected; it has no credentials, release permissions, environment, or external-action step.

`1.0.1` is the stable successor candidate to the published `v1.0.0` release. The published `v1.0.0` contains no native updater, so users on that release must manually install the first signed `1.0.1` installer; no in-place automatic migration is claimed. Release assembly refuses to reuse or move the existing public tag; compatibility changes after that tag require a versioned migration or an explicit documented refusal.

## Alternatives considered

- **Let Runtime install updates** — rejected because Runtime owns durable shared state, while native installation mutation belongs to Desktop Main or the standalone CLI transaction.
- **Ship a default production key and origin** — rejected because deployment trust and release locations require a separate audit and must remain absent until authorized.
- **Treat the reserved manifest root as ready** — rejected because a writer can fail after reservation; the inner `ready` rename is the complete-set publication point.
- **Combine signing and publication behind workflow booleans** — rejected because dormant external commands and credentials would give evidence collection authority to change release state.

## Consequences

Repository verification can establish the packaged automatic-update and rollback paths without granting external release authority. Operators must provide audited production trust and obtain each external approval separately. Native evidence remains platform-owned, and a local unsigned artifact remains only local evidence.
